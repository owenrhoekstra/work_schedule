1.Why this branch exists

The Django settings page (/schedule/settings/) still carries the pre-multi-tenancy surface — a grab bag of employee lists, Titles, and Roles with no navigation structure. The Role model is gone (Branch A), but the surface hasn't been rewritten. Team and membership models exist but have no UI. Meanwhile the schedule has moved to Vue, creating an inconsistency: the primary app is Vue, but settings is still Django templates.

This branch rewrites settings as a Vue surface with proper navigation, exposes the company/team/membership models through the UI for the first time, and settles the question of where employees are managed.

2.Scope

In scope

  • Restructure the Vue router so schedule and settings are siblings under one mount
  • Build /settings/* as a proper Vue surface with sidebar navigation
  • Expose Team CRUD, TeamRole management, TeamMembership admin grants, EmployeeTeam assignments
  • Surface the pending-membership queue and CompanyMembership admin grants
  • Move "Add Employee" from schedule into settings
  • Retire the Django settings surface

Not in scope

  • Retiring /schedule/employees/<uuid>/defaults/ (Django reading page). This page remains the per-employee edit surface — clicked from the schedule row, not from settings.
  • Team-scoped day override UI (deferred to a dedicated branch)
  • Combining the settings bulk view with the Django per-employee view into one surface (future; different needs for now)

3.Decisions

3.1 Route mount: single Vue mount at /

Currently router/app.ts bases at /schedule/, so every Vue route lives under /schedule/*. Settings at /settings/* would need either a third router branch (adds complexity) or the restructure.

Decision
Restructure. Base the app router at / and mount /schedule/* and /settings/* as sibling route trees. MenuBar becomes a shared shell with Schedule / Settings as equal-weight destinations.

3.2 Landing page: permission-based redirect

/settings/ redirects based on the user's highest available scope:

  • Platform admin or company admin → /settings/company/
  • Team admin (any team) → /settings/teams/
  • Member → /settings/profile/
Decision
One line of routing logic. First-impression per role.

3.3 Employee management split

Schedule click-through → Django reading page. Clicking an employee's name on the schedule continues to navigate to /schedule/employees/<uuid>/defaults/ (Django template). This page stays for now. It shows the employee's current pattern, full pattern history, and offers the entry points for pattern editing and identity editing (via /schedule/employees/<uuid>/details/).

Settings Employees tab → bulk view only. The settings Employees tab is for bulk operations: list with filter/search, active/former toggle, row selection, bulk actions. Clicking a row navigates to the same Django reading page. Settings does not duplicate per-employee edits.

Decision
The Django reading page was built for individual employee inspection and editing. It's been verified through QA and iteration (Sessions 6–9). Rebuilding it in Vue is a large lift with no user-facing benefit — the page already works. Settings is a different lens: bulk view for cross-employee work (who's on which team, who's been deactivated, who has no schedule). The two serve different needs.
Reversal from earlier sketch
The earlier design pass proposed retiring the Django reading page in this branch. Reverted. The reading page stays — it's the per-employee edit surface, not a sub-view of settings.

3.4 Role display in settings

The settings Employees list shows the employee's default team's role as the "Role" column. Matches the schedule row's subtext display (Kitchen — Head Chef). Clicking through to the Django reading page (or the drawer) reveals every team assignment.

3.5 Team-scoped day overrides: deferred

DayOverride.team exists but no UI surfaces it. The schedule currently renders company-wide day overrides only. Deferring the settings UI for team-scoped overrides to a dedicated branch, after the schedule also renders team-scoped statuses.

4.Settings surface

Route tree

/settings/
  ├── company/              Company profile
  ├── employees/            Bulk employee view
  ├── teams/                Team list + CRUD
  ├── teams/:id/            Team detail
  ├── titles/               Company-wide title labels
  ├── members/              Pending approvals + admin grants
  └── profile/              Personal settings (own user)

Navigation: left sidebar on desktop (md+), drawer or stacked on mobile.

4.1 Company profile

Editable by company admin (and platform admin).

Fields: name, slug, site_url, app_name, allow_member_view_all.

Danger zone: no delete UI. Deleting a company is platform-admin scope via Django admin.

4.2 Employees (bulk)

Editable by company admin.

  • Search by name/email
  • Active / Former toggle (default: active)
  • Sortable columns: name, team, role, start_date, last_day
  • Bulk selection with actions:
    • Deactivate selected (opens a "last day" input, applies to all selected)
    • Assign selected to team (dropdown, applies to all)
    • Add Employee button → modal (name, email, start_date, title — no team assignment on create; team assigned separately)
  • Click a row → /schedule/employees/<uuid>/defaults/ (full-page Django nav)
Deferred if complexity is high
Bulk actions beyond search/filter can ship in a follow-up. Minimum viable: search + active/former toggle + click-through + Add Employee button.

4.3 Teams

Editable by company admin (all teams) or team admin (own teams only).

List view:

  • Add team button (company admin only)
  • Each row: name, member count, allow_member_view_all toggle
  • Click a row → team detail

Team detail:

  • Edit name + allow_member_view_all (team admin or company admin)
  • Delete team (company admin only — guard against existing members)
  • Members section: current EmployeeTeam assignments + add/remove
  • Admins section: current TeamMembership admins + grant/revoke (company admin only)
  • Roles section: TeamRole list + add/reorder/delete

4.4 Titles

Editable by company admin.

Company-wide title labels (Dr., Ms., Mr. etc.). Fork-per-team deferred — titles stay company-wide.

4.5 Members

Editable by company admin.

  • Pending membership queue (approve / reject)
  • Current company admins list with grant/revoke controls
  • Current active members list (read-only, link to their Employee row if one exists)

4.6 Profile

Any authenticated user.

  • First name, last name
  • Email
  • Password change (link to existing OTP-gated flow)
  • OIDC identity management (link to accounts surface)
Note on name sync
Today User.first_name/last_name and Employee.first_name/last_name are separate. Profile edits the User row. Employee rows are edited via the Django employee page. The relationship is intentional — a user can display differently per company. Profile shows the User-level name; per-company Employee names are managed elsewhere.

5.Schedule surface delta

Schedule itself doesn't change in this branch. Two deltas:

  1. MenuBar restructure. Schedule and Settings become equal-weight destinations. Profile moves into settings sidebar — it's no longer a top-level destination.
  2. Add Employee removed from schedule toolbar. Moves to Settings → Employees.

8.Data flow examples

8.1 Bulk deactivate

  1. User selects 3 rows in /settings/employees/, clicks "Deactivate selected"
  2. Modal opens, asks for a last-day date
  3. Submit → POST /api/v1/employees/bulk-deactivate/ with {employee_ids: [...], last_day: "..."}
  4. Server applies the same deactivation logic as individual deactivate
  5. Response: success count + list of any failures (e.g., "already deactivated")
  6. Client invalidates ["employees"] query, refreshes table

8.2 Grant team admin

  1. Company admin navigates to /settings/teams/:id/
  2. "Admins" section shows current admins
  3. Click "Grant admin" → user picker modal
  4. Submit → POST /api/v1/teams/<id>/memberships/ with {user_id}
  5. Response: created TeamMembership
  6. Client invalidates ["team", id], refreshes

8.3 Assign employee to team

  1. Team admin navigates to /settings/teams/:id/
  2. "Members" section shows current assignments
  3. Click "Assign employee" → employee picker modal
  4. Submit → POST /api/v1/teams/<id>/employees/ with {employee_id, is_default, valid_from}
  5. Response: created EmployeeTeam
  6. Client invalidates ["team", id] and ["week"] (roster changes)
